# Правила объединения файлов и реестра

## Состав представления

Предлагается использовать три составляющие: основную систему как нижний слой, локальные данные контейнера как верхний слой и метаданные скрытых объектов. Правила ниже описывают желаемый контракт WinLayer, а не готовые возможности одного Windows API.

| Состояние | Значение |
| --- | --- |
| Локальный объект | Файл, каталог, ключ или значение, созданное либо изменённое в контейнере |
| Метка удаления | Объект скрыт внутри контейнера, даже если существует в основной системе |
| Непрозрачный каталог или ключ | Его локальное содержимое видно, но отсутствующие дочерние объекты не дополняются из нижнего слоя |
| Обычный локальный каталог или ключ | Его содержимое объединяется с нижним слоем |

Метки удаления называют также `tombstone` или `whiteout`, а копирование при изменении — `copy-on-write` или `copy-up`.

## Чтение

Сначала проверяются политика доступа и состояние всех предков объекта. Удалённый предок делает путь недоступным. Непрозрачный предок запрещает подмешивать нижнее содержимое, но разрешает существующие локальные дочерние объекты.

Затем проверяются метка удаления самого объекта и локальные данные. Только если локального объекта действительно нет, нет запрета на нижний слой и чтение разрешено, используется основная система.

Ошибки «доступ запрещён», повреждение данных, занятый файл или ошибка ввода-вывода не являются отсутствием объекта. После них нельзя молча читать внешний вариант. Локальный файл нулевой длины и пустое значение реестра тоже являются полноценными объектами.

Чтение внешних данных выполняется с правами соответствующего пользователя. Привилегированный управляющий процесс не должен превращать недоступные пользователю системные данные в доступные локальные копии.

## Запись

Для создания нового файла нижний слой не нужен. При частичном изменении, дописывании или изменении метаданных существующего внешнего файла сначала подготавливается локальное представление, сохраняющее необходимые исходные данные. При полном замещении содержимого копирование старых байтов обычно можно пропустить.

Режим открытия файла существенен: «создать только новый» должен учитывать объект в объединённом представлении и возвращать конфликт, если он уже существует. «Открыть существующий» не должен создавать отсутствующий файл. Успешный запрос прав на запись не должен выдавать приложению дескриптор, позволяющий менять нижний слой.

Копирование необходимо завершить до предоставления изменяемого объекта приложению. Нельзя дождаться только вызова `WriteFile`: запись возможна через отображение файла в память, усечение, изменение атрибутов и другие операции.

Предлагается отделить право изменить виртуальную копию от права менять оригинал. Например, политика может разрешить локальную запись в виртуальный `Program Files`, не выдавая права записи в настоящий каталог. Это решение не разрешает читать защищённый оригинал и не отменяет явно запрещённые области.

## Удаление и повторное создание

Удаление существующего внешнего файла создаёт метку удаления. Удаление локального файла тоже должно скрыть одноимённый нижний объект, если он есть или появится позднее. Предлагаемая последовательная политика — сохранять метку для каждого успешно удалённого логического объекта.

Удаление несуществующего объекта возвращает соответствующую ошибку. Удаление непустого каталога следует контракту конкретного API: обычное удаление каталога не превращается в рекурсивную операцию автоматически.

После удаления каталога и создания нового с тем же именем старые внешние дети не должны появляться вновь. Поэтому метка удаления заменяется новым локальным непрозрачным каталогом. Аналогично обрабатывается удалённая и затем созданная заново ветка реестра.

Нельзя одновременно хранить активную метку удаления объекта и считать этот же объект видимым. Изменение таких состояний — одна логическая операция метаданных.

## Переименование и перемещение

Для внешнего файла `A` операция переименования в `B` означает:

1. Проверить источник и допустимость назначения в объединённом представлении, включая флаги замены существующего объекта.
2. Подготовить локальный результат `B`, содержащий видимое содержимое `A`.
3. Опубликовать `B` и скрыть `A` как одно согласованное изменение виртуального пространства имён.
4. Сохранить оба внешних объекта без изменений.

Если `A` уже существует локально, его данные можно переместить внутри верхнего слоя. Но старое имя всё равно требует метки удаления, чтобы не проявился одноимённый нижний объект.

При переименовании каталога или ключа нужно сохранить всё видимое поддерево. Для первого варианта проще материализовать его локально, применив имеющиеся изменения и метки, а результат сделать непрозрачным. Иначе под новым именем могут неожиданно появиться дети из одноимённой внешней ветки. На больших деревьях это дорого; ленивое перенаправление поддеревьев — отдельное усложнение.

Копирование отличается отсутствием скрытия источника. Оно читает объединённое представление, поэтому должно учитывать локальные изменения и скрытых детей. Перемещения между виртуальными томами сохраняют ограничения используемого Windows API: нельзя объявлять их атомарным переименованием только потому, что физически оба слоя находятся на одном диске.

## Перечисление

Список файлов, подкаталогов, ключей и значений формируется объединением локальных и внешних имён. Локальная запись имеет приоритет при совпадении; метки удаления исключают объекты; непрозрачность исключает нижних детей целиком.

Объединение требуется не только для `FindFirstFile` и `RegEnumValue`, но и для соответствующих низкоуровневых запросов. Размеры, количество элементов и сведения о типах должны соответствовать выдаваемому представлению. Для одного прохода перечисления нужен согласованный курсор, иначе изменения между вызовами приводят к повторениям и пропускам.

## Особенности реестра

Ключ — контейнер значений и подчинённых ключей. Изменение одного значения не должно скрывать соседние значения нижнего слоя. Для обычных операций предпочтительна детализация по отдельным значениям; полная материализация поддерева нужна, например, при его переименовании.

Пример: внешняя ветка содержит `Theme=Light` и `Language=ru`. После локального изменения `Theme=Dark` приложение видит `Theme=Dark` и внешний `Language=ru`. После удаления `Language` появляется метка именно для этого значения. Пустое имя значения по умолчанию нужно хранить отдельно от отсутствия значения.

Следует сохранять тип и исходные байты: строки, многострочные значения, бинарные данные и числовые типы нельзя без потерь превращать в произвольные JSON-строки. Значения `REG_EXPAND_SZ` хранятся без самовольной подстановки переменных окружения.

WOW64 предоставляет отдельные представления части реестра для 32- и 64-разрядных приложений; некоторые ветки общие. Схема должна учитывать представление, а не просто создавать одинаковые независимые копии всего дерева. [Registry Redirector](https://learn.microsoft.com/en-us/windows/win32/winprog64/registry-redirector).

`HKEY_CLASSES_ROOT` уже объединяет сведения из пользовательской и машинной веток `Software\Classes`. Его нельзя реализовать как третий полностью независимый набор настроек. [Merged View of HKEY_CLASSES_ROOT](https://learn.microsoft.com/en-us/windows/win32/sysinfo/merged-view-of-hkey-classes-root).

## Сведения о диске и доступном месте

Предлагается согласовать сведения о свободном месте с фактическим назначением записи. Если виртуальный `C:` записывается в папку на `D:`, проверка доступного места для такой установки должна учитывать хранилище контейнера. Для явно подключённого каталога с прямой записью используется его место назначения. Несколько виртуальных дисков, размещённых на одном физическом томе, не получают независимые запасы свободного места.

Один из способов запроса в Windows — `GetDiskFreeSpaceExW`, который учитывает доступный пользователю объём и квоты. Перехват одного этого API не считается доказательством совместимости всех установщиков: используемые целевым ПО способы проверки устанавливаются экспериментом. [Документация Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw).

Нехватка места или недоступность хранилища не меняют политику записи и не разрешают использовать оригинал хоста как запасной путь. Предложены настройки виртуальных букв, фиксированной и динамической ёмкости; свободное место учитывает незаполненные фиксированные лимиты без повторного вычитания уже занятых байтов. [Диски, квоты и исключения для папок](12-Virtual-Disks-and-Quotas.md).

## Открытые дескрипторы и параллельная работа

У открытого объекта должна быть устойчивая логическая идентичность. Если один процесс открыл внешний файл для чтения, а другой вызвал создание локальной изменяемой копии, простой перехват путей оставит первый дескриптор привязанным к старому файлу. Это может нарушить ожидаемую согласованность чтения и записи.

До обещания общей поддержки нужно выбрать и проверить механизм согласования дескрипторов и отображений памяти. Возврат реальных дескрипторов нижнего слоя не решает эту задачу автоматически. То же относится к открытым ключам после переименования, режимам совместного доступа, блокировкам и отложенному удалению.

Два процесса не должны одновременно создать разные локальные копии одного объекта. Требуется координация на уровне контейнера и логического объекта. Идентификатор объекта должен учитывать альтернативные пути и ссылки, а не только строковое имя.

## Хранение и восстановление

Предлагаемая структура одной среды:

```text
ExampleBox/
  container.json
  Files/
    C/
      Program Files/
        Example/
          Example.exe
    D/
  Registry/
    local.hiv
  Metadata/
    overlay.db
  Logs/
```

Это проектная схема, файлы контейнера пока не созданы. `container.json` содержит идентификатор, отображения дисков, точки запуска и политику; `local.hiv` — локальные данные реестра; `overlay.db` — метки, непрозрачность и журнал операций. Конкретный формат метаданных зависит от выбранного движка. При использовании Sandboxie следует принять его собственную схему хранения.

Файловые изменения, запись в куст и транзакция базы метаданных не становятся одной атомарной операцией сами по себе. Для операций из нескольких шагов нужен журнал подготовки и завершения с восстановлением после сбоя. Движок должен скрывать промежуточные состояния и не сообщать об успешном переименовании до выполнения принятого контракта фиксации.

Первый вариант может использовать живую основную систему: изменения в ней видны там, где ещё нет локальных переопределений. Такая среда не является снимком. Согласованное копирование изменяющегося внешнего дерева требует проверки конфликтов или отдельного механизма снимков; при обнаруженном конфликте операция должна завершаться ошибкой или повторяться, а не публиковать смесь версий.
