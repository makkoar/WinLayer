# Участие в разработке WinLayer

Начните с [плана разработки](https://github.com/makkoar/WinLayer/issues/15) и существующих issue. Перед существенным изменением создайте задачу с конкретным результатом, границами работы и проверяемыми критериями приёмки. Для ошибки укажите версию Windows, архитектуру процесса, шаги воспроизведения, ожидаемое и фактическое поведение.

## Задачи и изменения

- `area:*` обозначает компонент, `priority:high/middle/low` — очередность; `enhancement`, `bug`, `documentation`, `tracking` — тип работы.
- Укажите зависимости ссылками на другие issue. Независимые задачи можно выполнять параллельно.
- Создавайте ветку от актуального `main`: `feature/TASK-<номер issue>`, `bugfix/TASK-<номер issue>` или `hotfix/TASK-<номер issue>` по назначению изменения.
- Один PR должен решать понятную задачу. В описании приведите изменение поведения, способ проверки и известные ограничения. `Closes #номер` используйте, когда все критерии задачи действительно выполнены.
- Не добавляйте временные результаты сборки, пользовательские данные, локальные конфигурации и ключи подписи.

## Среда разработки

Управляемая часть использует C# 14, .NET 10 и Avalonia. `global.json` допускает SDK 10.0.100 и более новые feature band ветки 10.0, включая preview; автоматический переход на SDK 11 запрещён. Для сборочных сценариев необходим PowerShell 7 (`pwsh`).

Для нативной части используется Visual Studio 2026: установите рабочую нагрузку «Разработка классических приложений на C++», инструменты MSVC v145 для x86/x64, Windows SDK и WDK ветки 28000 с интеграцией драйверных проектов. Microsoft поддерживает VS 2026 с WDK 28000.2526; номера сборки SDK и WDK должны совпадать, номера исправлений могут различаться. [Установка WDK и компонентов Visual Studio](https://learn.microsoft.com/en-us/windows-hardware/drivers/download-the-wdk).

Требуемый набор инструментов и версия SDK заданы в [Directory.Build.props](Directory.Build.props); драйвер использует собственный `WindowsKernelModeDriver10.0`. Для C/C++ нужен MSBuild из Visual Studio, а не только `dotnet build`. Установленные компилятор, SDK и WDK проверяются отдельно от наличия самой IDE.

Основная ОС — Windows 11 x64, минимальная — Windows 10 22H2 x64 всех редакций. Успешная компиляция не заменяет проверки совместимости.

## Структура и зависимости

Явные импорты C# размещайте в `Imports.cs` соответствующего проекта как `global using`; `ImplicitUsings=true`. Конфликты имён предпочтительно решать глобальными алиасами.

Все версии NuGet-пакетов указываются только в `Directory.Packages.props`, а подключения — в проектах без атрибута `Version`. `packages.lock.json` не используется. Общие параметры C# и C/C++ находятся в отдельных блоках `Directory.Build.props`; действия перед публикацией — в `Directory.Build.targets`. Не переносите параметры пользовательской среды выполнения в драйвер ядра.

## Автоматические правила

Источники требований к стилю и форматированию — [.editorconfig](.editorconfig), [.gitattributes](.gitattributes) и подключённые анализаторы. Их правила здесь не дублируются. `.editorconfig` будет расширяться; обнаруженные нарушения исправляйте в рамках текущей задачи, без отключения правил и подавления диагностики ради успешной сборки.

## Автодокументация и ручные проверки

- Комментарии, сообщения исключений, собственные логи и автодокументация пишутся по-русски.
- Документируйте новые типы, функции и свойства, включая приватные. При изменении существующего кода проверяйте полноту и актуальность его документации.
- `<summary>` кратко описывает назначение типа или члена. Не перечисляйте в нём проверки и шаги реализации, не пересказывайте код. Само изменение кода не является поводом расширять сводку.
- Изменения контракта отражайте в соответствующих тегах: `<param>`, `<returns>`, `<remarks>`. Описывайте параметры и результат функции, кроме возврата простого `Task`. Исключения отдельными XML-тегами не перечисляйте.
- Для переопределений используйте `<inheritdoc />`. Добавляйте `<remarks>` только для существенной особенности реализации относительно унаследованного контракта; не повторяйте сводку, параметры и общий контракт.
- Каждый XML-тег автодокументации занимает одну строку; для смыслового переноса используйте `</br>`.
- В XML-файлах проекта разделяйте блоки одной пустой строкой, оставляйте такую же строку после открывающего корневого тега и перед закрывающим.

Формат прототипа ещё формируется. Не вводите миграционные слои и обратную совместимость без отдельной задачи.

## Проверка изменений

Каждый `[Fact]` и `[Theory]` должен иметь собственный `DisplayName` на русском языке, описывающий проверяемое поведение.

Тесты используют xUnit v3 4.0.2 с Microsoft.Testing.Platform v2 и `coverlet.MTP`. Выбор платформы задан в `global.json`, настройки измерения — в `Tests/WinLayer.Tests/testconfig.json`.

Из корня репозитория:

```powershell
dotnet build WinLayer.slnx -c Debug
dotnet test --project Tests/WinLayer.Tests/WinLayer.Tests.csproj -c Debug
pwsh -NoProfile -File Build/Test-Coverage.ps1 -Configuration Debug
pwsh -NoProfile -File Build/Test-Coverage.ps1 -Configuration Release -RequireFullCoverage
```

Coverlet измеряет весь C#-код продукта, включая службу, CLI и панель. Перед публикацией требуется **100% строк, ветвей и методов в каждой продуктовой сборке**. Непокрытая сборка остаётся в отчёте с нулевыми значениями; дополнительная проверка отклоняет отчёт, в котором отсутствует проект. Не исключайте код, свойства, UI или системные адаптеры ради прохождения порога.

Обычная сборка не запускает тесты автоматически. `dotnet publish` запускает проверку покрытия и прекращается при недостижении порога. Новые изменения должны сохранять полное покрытие; успешный отчёт предыдущего запуска не заменяет повторную проверку. Нативные компоненты Coverlet не измеряет.

Проверки используют настоящие локальные каналы Windows и жизненный цикл панели Avalonia, поэтому запускаются на Windows с доступной оконной средой. На время проверки диагностическая служба WinLayer должна быть остановлена: тесты сами занимают её канал и завершают созданные хосты. Тесты выполняются последовательно, поскольку исполняемые компоненты используют общее имя канала и единственный экземпляр приложения Avalonia.

Проверяйте поведение и границы контрактов: повреждённые сообщения, обрывы соединения, ошибки доступа, несовместимые версии, повторные операции. Одного теста, повторяющего реализацию, недостаточно.

## Драйвер и нативные библиотеки

Собирайте DLL и диагностический клиент в Win32 и x64; драйвер — только x64. В бинарном протоколе запрещены указатели и зависимые от архитектуры размеры. Изменение протокола требует синхронного изменения C# и нативного контракта, проверок ABI и версии.

Подпись, установку, загрузку, Driver Verifier и выгрузку драйвера проверяйте на отдельной тестовой Windows с возможностью отката. Не меняйте параметры загрузки рабочей системы ради проверки PR. Фиксируйте конфигурацию стенда и фактический результат; наличие исходников не считается успешным испытанием ядра.

WinLayer пока не является границей безопасности для недоверенного ПО. Не обозначайте как реализованные виртуализацию, наследование контекста и переносимость до проверки соответствующих сценариев. [Текущее устройство прототипа](Docs/14-Prototype.md).
