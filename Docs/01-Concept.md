# Концепция WinLayer

## Назначение

Программа должна позволять запустить установщик в отдельной среде, собрать установленные файлы, настройки, кэши и последующие обновления в папке контейнера, а затем запускать установленное приложение через ярлык. Основной сценарий — ПО, которое даже при выборе диска `D:` размещает часть компонентов на `C:`, например Visual Studio. Папка остаётся доступной пользователю через Проводник. Несколько приложений могут использовать одну среду, если им нужно обмениваться настройками.

Основная цель — сохранить установленное ПО в одном управляемом месте и повысить его переносимость. Доступ на чтение к основной системе нужен для совместимости чувствительных приложений. Он одновременно связывает контейнер с конкретным компьютером, поэтому переносимость необходимо проверять отдельно.

## Исходные требования

1. Исполняемые файлы приложения лежат внутри папки контейнера. Специальный ярлык запускает их через управляющую программу.
2. Чтение реестра сначала использует локальные данные; при их отсутствии обращается к реестру основной системы.
3. Создание и изменение данных реестра остаётся в контейнере. Переименование существующего системного ключа создаёт локальное представление результата.
4. Приложение использует привычные пути вроде `C:\Folder\file.txt`, но записывает в соответствующую подпапку контейнера.
5. Недостающие локальные файлы читаются из основной системы. Изменение существующего внешнего файла создаёт его локальную версию.
6. Дочерние процессы по умолчанию наследуют среду, включая запускаемые установщиком вспомогательные программы и процессы, создаваемые уже установленным приложением. Явно разрешённые внешние действия, например открытие веб-ссылки обычным браузером, выполняются через отдельного посредника.
7. Обновление, восстановление и удаление выполняются в той же среде. Требование относится ко всему жизненному циклу установки.
8. Работа, переданная службе или системному посреднику, также должна оставаться локальной либо явно отклоняться как неподдерживаемая. Это техническое следствие требования чистой основной системы.
9. Ярлыки контейнерного ПО доступны снаружи через управляемые ярлыки WinLayer. Их цель разрешается с учётом среды; обработчик запускается в ней либо получает явно разрешённое внешнее действие.
10. Созданные или изменённые локальные записи установки получают отдельные представления в списке программ Windows. Удаление и обслуживание через них относятся к контейнеру, а не к одноимённому продукту хоста.
11. Контейнер можно открыть самостоятельно: посмотреть его программы, реестр, процессы, занимаемое место и выполнить доступные действия управления.
12. Открытие ссылок должно по возможности сохранять привычные авторизации пользователя. Предложен режим обычного внешнего браузера с настоящим профилем и загрузками хоста. Альтернатива — изолированный браузер с постоянной локальной копией профиля либо свежей внешней основой на каждый сеанс. Окончательный режим по умолчанию пока не выбран.
13. Специальные URI-схемы, включая ссылки запуска приложения и возврата авторизации, направляются к выбранному контейнерному обработчику через WinLayer. Несколько установок одной программы требуют явного выбора маршрута, а ответы авторизации — однозначного сопоставления с запросом.
14. Рабочие папки, требующие прямого доступа к внешним файлам, задаются исключениями в конфигурации контейнера. Для них изменения затрагивают оригиналы, а не локальные копии.
15. Поддержанные EXE, BAT, CMD и другие файлы можно быстро запускать в выбранном контейнере из контекстного меню Проводника.

Стек проекта — C#, .NET 10 и стабильная Avalonia для интерфейса. Выбран гибридный движок: собственный драйвер, DLL x86/x64 и служба. Основное приложение публикуется как x64/SingleFile, нативные файлы могут находиться рядом. Windows 11 — основная ОС, Windows 10 22H2 — минимальная цель; первый прототип начинается с простого ПО. [Принятые решения](13-Implementation-Options.md). Также предложены настраиваемые виртуальные диски с буквами и фиксированной либо динамической ёмкостью. [Правила расчёта и исключений](12-Virtual-Disks-and-Quotas.md) пока являются проектным предложением; они не означают создания настоящих разделов хоста.

Управляемые внешние ярлыки, записи программ и опубликованные обработчики схем — разрешённая интеграция с хостом. Она не распространяется на произвольные записи установщика. Разрешённый внешний браузер изменяет данные хоста обычным образом. Для перемещаемых чужих ярлыков предлагается сохранять оригинал хоста и публиковать отдельную контейнерную версию. Подробные правила приведены в [описании интеграции](08-Host-Integration.md) и [внешних приложений и протоколов](10-External-Applications-and-Protocols.md), состав интерфейса — в [описании панели](09-Container-Manager.md).

Принятое исходное условие: контейнеры подготавливаются на чистой Windows. Проблема пропуска компонентов из-за уже установленного на хосте ПО исключена из объёма первой версии. Автоматический сбор внешних зависимостей не требуется.

Слово «контейнер» здесь обозначает среду приложения. Требование отдельного ядра Windows или полного образа операционной системы в исходной идее отсутствует.

## Как понимать изменение внешнего объекта

Пусть в основной системе есть `C:\Settings\app.ini`, а в контейнере его ещё нет.

| Действие приложения | Результат внутри контейнера | Основная система |
| --- | --- | --- |
| Прочитать файл | Читается внешний файл | Без изменений |
| Изменить одну строку | Создаётся локальная копия с изменённой строкой | Исходный файл сохранён |
| Полностью перезаписать файл | Создаётся локальный файл с новым содержимым | Исходный файл сохранён |
| Переименовать в `other.ini` | Локальный `other.ini`, старое имя скрыто | Сохраняется `app.ini` |
| Удалить | Старое имя скрыто меткой удаления | Файл продолжает существовать |
| Скопировать в `other.ini` | Создаётся локальный `other.ini`, исходное имя остаётся видимым | Без изменений |

Это и есть смысл пунктов 2.3 и 3.3. Для переименования недостаточно создать результат: требуется ещё скрыть исходное имя. Для копирования скрывать исходное имя, наоборот, нельзя.

В реестре аналогично: изменение значения создаёт локальную версию значения, а переименование ключа должно сохранить видимые значения и подчинённые ключи под новым именем и скрыть старую ветку.

## Физические и виртуальные пути

Удобное отображение:

```text
Видимый приложению путь: C:\Program Files\Example\Example.exe
Реальный путь:           D:\Containers\Example\Files\C\Program Files\Example\Example.exe

Видимый приложению путь: C:\Folder\result.txt
Реальный путь:           D:\Containers\Example\Files\C\Folder\result.txt
```

Двоеточие из обозначения диска не становится частью имени вложенного каталога. `Files\C` — корень виртуального диска, а `Files\D` может представлять другой диск. Сама папка с EXE остаётся обычной папкой программы внутри виртуального диска; размещать каждое приложение непосредственно в корне `C:\` необязательно.

Простая смена рабочего каталога процесса этого не даёт. Абсолютные пути, системные каталоги, загрузка DLL и обращения по дескрипторам требуют участия механизма виртуализации.

## Ближайшие готовые решения

| Решение | Что совпадает с идеей | Где проходит различие |
| --- | --- | --- |
| Sandboxie Plus | Локальные файлы, отдельный реестр, чтение внешних объектов, запуск приложений в песочнице | Близкий технический аналог; WinLayer использует собственную реализацию |
| Windows Sandbox | Изолированный Windows-сеанс с отдельным ядром | Временная виртуальная машина; закрытие уничтожает внутреннее состояние, внешний доступ организуется через общие папки |
| Windows Containers | Контейнеризация Windows-нагрузок | Не предназначены для обычных приложений с интерактивным рабочим столом |
| MSIX | Виртуальные представления некоторых файлов и разделов реестра | Правила зависят от типа приложения и расположения данных; упаковка не означает перенаправление всех записей |

У Sandboxie описаны приоритет локальной копии, чтение оригинала и хранение локального реестра в файле куста. Это подтверждает практическую реализуемость базовой модели. [Sandbox Hierarchy](https://sandboxie-plus.github.io/sandboxie-docs/Content/SandboxHierarchy.html).

Windows Sandbox использует аппаратную виртуализацию; при закрытии внутреннее состояние удаляется. Общие папки с разрешённой записью могут сохранять изменения на хосте. [Обзор](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/), [настройка общих папок](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file).

Microsoft отдельно указывает, что Windows Containers не поддерживают приложения, которым нужен графический интерфейс рабочего стола. [Ограничения Windows Containers](https://learn.microsoft.com/en-us/virtualization/windowscontainers/quick-start/lift-shift-to-containers).

У MSIX есть объединённые представления, но существуют и разрешённые записи за пределами виртуализируемых областей. Поэтому он не заменяет описанную политику «все поддерживаемые изменения только локально». [Поведение упакованных приложений](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes).

## Предлагаемое направление

Приоритет — локализация установки и обновлений доверенного ПО. Простой установщик годится для проверки основы, но не заменяет целевой сценарий Visual Studio. Повышение прав, MSI и работа через службы должны исследоваться в начале проекта: откладывание этих вопросов создаёт риск получить движок, который не решает основную задачу.

Если цель — быстрее получить полезный инструмент, первым кандидатом будет оболочка управления над существующим движком. Если цель — собственная технология виртуализации, сначала нужен эксперимент с файлами, реестром, дочерним процессом и установкой через системного посредника. Интерфейс и удобные ярлыки следует строить после подтверждения этой основы. Для нагрузок, которым обязательно нужны реальные изменения ядра или компонентов Windows, потребуется другой режим, например виртуальная машина.
