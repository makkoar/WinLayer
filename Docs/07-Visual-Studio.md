# Установка Visual Studio в одну папку

## Целевой результат

Visual Studio остаётся последующим сложным сценарием. Первый прототип проверяется на более простом ПО; прохождение описанных ниже шагов не является условием его первого рабочего результата.

Пользователь создаёт контейнер на `D:`, запускает в нём установщик Visual Studio и позволяет ему использовать привычные пути `C:\Program Files`, `C:\ProgramData`, профиль пользователя и реестр. Физически поддерживаемые изменения попадают в папку контейнера. Затем IDE, её инструменты и обновляющие процессы запускаются с тем же представлением системы.

Контейнер подготавливается на чистой Windows. Отсутствие ранее установленных сторонних компонентов — принятое условие; автоматический сбор зависимостей не нужен.

## Почему выбор диска в установщике недостаточен

Microsoft прямо указывает, что часть инструментов и SDK устанавливается на системный диск даже при выборе другого расположения. Отдельно настраиваются IDE, кэш загрузки и общие компоненты. [Выбор расположения установки](https://learn.microsoft.com/en-us/visualstudio/install/change-installation-locations?view=visualstudio).

Начальный загрузчик устанавливает отдельную программу Visual Studio Installer, а начальная установка требует административных прав. Поэтому виртуализация должна начинаться с загрузчика, до установки самого Installer. [Установка Visual Studio](https://learn.microsoft.com/en-us/visualstudio/install/install-visual-studio?view=visualstudio).

Ожидаемое отображение выглядит так:

| Путь, используемый установкой | Физическое размещение в контейнере |
| --- | --- |
| `C:\Program Files\...` | `D:\Containers\VS\Files\C\Program Files\...` |
| `C:\Program Files (x86)\...` | `D:\Containers\VS\Files\C\Program Files (x86)\...` |
| `C:\ProgramData\...` | `D:\Containers\VS\Files\C\ProgramData\...` |
| `C:\Users\<профиль>\AppData\...` | Соответствующая ветка внутри `Files\C\Users` с согласованным отображением профиля |
| Временные файлы установки | Виртуальный временный каталог внутри контейнера |
| Машинные и пользовательские настройки | Локальный реестр контейнера с сохранением различий веток и представлений |

Таблица описывает целевую политику, а не полный список фактических путей любой версии Visual Studio.

## Весь цикл обслуживания

Изолировать требуется загрузчик, Visual Studio Installer, его обновление, установку пакетов, запускаемые помощники, последующие обновления продукта и восстановление. Запуск IDE сам по себе проверяет только небольшую часть этого цикла.

Для выбранной нагрузки нужно проверить сборку и отладку небольшого проекта: компилятор, MSBuild, тестовые процессы и другие инструменты должны работать в том же контейнере. Создаваемые IDE обычные дочерние процессы наследуют его автоматически по правилам WinLayer.

Операции, переданные внешним службам, требуют отдельной поддержки. Windows Installer умеет выполнять установку и восстановление с повышенными правами от имени пользователя; одного ограничения исходного окна установщика недостаточно. [Windows Installer и UAC](https://learn.microsoft.com/en-us/windows/win32/msi/using-windows-installer-with-uac).

Не следует считать, что любой компонент VS использует одинаковый механизм установки. Конкретные цепочки исполнителей и служб устанавливаются наблюдением за выбранной версией и нагрузкой.

## Где возможны ограничения

Для обычных пользовательских компонентов виртуализация файлов, реестра и поддерживаемых служб соответствует задаче. Если конкретная нагрузка требует реального драйвера или включения возможности Windows, запись их файлов в контейнер не активирует их в отдельной системе: отдельного ядра здесь нет.

Такие компоненты могут стать внешним системным требованием или потребовать режима виртуальной машины. Молча устанавливать их на хост нельзя, если выбран контракт полной локализации прикладной установки.

Sandboxie документирует работу Windows Installer и ряда служб в песочнице и остаётся техническим аналогом. Поддержку выбранной конфигурации VS нужно независимо проверить для механизма WinLayer. [Службы Sandboxie](https://sandboxie-plus.github.io/sandboxie-docs/Content/ServicePrograms/).

## Перенос и обновление после переноса

Виртуальные пути должны оставаться прежними при смене физического расположения контейнера. Особое внимание требуется путям к источникам установки: Visual Studio сохраняет путь локального набора пакетов и использует его при обслуживании. Microsoft предупреждает, что перенос такого набора может нарушить поиск пакетов. [Локальная установка Visual Studio](https://learn.microsoft.com/en-us/visualstudio/install/create-an-offline-installation-of-visual-studio?view=visualstudio).

Следовательно, если набор пакетов включён в контейнер, Installer должен видеть устойчивый виртуальный путь к нему. Локальный набор установочных пакетов сам по себе ещё не является переносимой установленной Visual Studio.

На целевом компьютере нужны совместимая Windows и движок WinLayer. Вход в учётную запись и лицензирование проходят штатно. Перенос между пользователями требует согласованного отображения профиля и реестра; массовая замена строк путей во всех файлах не является надёжным решением.

## Последующий эксперимент с Visual Studio

1. Подготовить отдельную чистую Windows и зафиксировать её базовую конфигурацию.
2. Выбрать точную версию, редакцию и небольшой полезный набор компонентов Visual Studio.
3. Установить движок-кандидат и создать пустую среду на `D:`.
4. Запустить загрузчик через среду и проследить установку, включая повышение прав и вспомогательные процессы.
5. Проверить внешние изменения и отдельно запуск, сборку, отладку, обновление и восстановление.
6. Остановить среду, перенести папку на другой путь и на вторую чистую систему с движком; повторить основные операции.

Эксперимент ещё не выполнялся. Гибридная основа WinLayer уже выбрана; этот этап после простого ПО устанавливает реальную границу поддержки VS и её обслуживания.
