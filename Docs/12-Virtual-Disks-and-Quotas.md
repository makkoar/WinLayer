# Виртуальные диски, квоты и исключения для папок

## Статус решений

В настройках контейнера предусматриваются видимые диски, их буквы и фиксированная либо динамическая ёмкость. Рабочие каталоги подключаются через исключения в конфигурации контейнера. Ниже описаны предлагаемые правила расчёта и применения; детали распределения между несколькими динамическими дисками ещё не выбраны окончательно.

Ёмкость в этом документе относится к дисковому пространству, а не к оперативной памяти. Это виртуальное представление для приложений контейнера: создание настоящих разделов или присвоение букв дискам хоста не требуется по модели продукта. Физические файлы верхнего слоя остаются в обычных подпапках контейнера. Возможность обеспечить такое представление должна быть проверена в выбранном движке.

## Настройки дисков

| Параметр | Смысл |
| --- | --- |
| Идентификатор | Устойчивая идентичность виртуального диска, не зависящая от буквы |
| Буква и метка | Например, `C:` и «Система», `E:` и «Данные»; буквы уникальны внутри контейнера |
| Источник чтения | Нижний каталог/том хоста либо отсутствие нижнего слоя для пустого диска |
| Локальный каталог | Подпапка контейнера, содержащая изменяемый верхний слой этого диска |
| Режим ёмкости | Фиксированный или динамический |
| Фиксированная ёмкость | Максимум учтённого локального объёма; задаётся в фиксированном режиме |
| Верхняя граница динамического роста | Необязательный максимум для динамического диска |
| Доля свободного остатка | Возможный способ распределения между несколькими динамическими дисками |

У физического хранилища дополнительно задаётся запас свободного места для основной системы и служебных операций WinLayer. Он применяется один раз к общему физическому тому, а не повторно для каждой виртуальной буквы. Размеры хранятся в байтах; интерфейс явно различает десятичные и двоичные единицы.

Список дисков, разрешение путей, сведения о томах и запросы свободного места должны соответствовать друг другу. Недостаточно изменить буквы только в панели. Для первого прототипа предлагается сохранять ожидаемую приложениями букву системного диска. Её смена в уже установленной среде требует отдельной поддержки сохранённых путей.

## Ёмкость и свободное место

В фиксированном режиме фиксируется общая ёмкость, а не постоянно одинаковое количество свободных байтов. Например, диск на 200 ГиБ с 50 ГиБ локальных данных имеет не более 150 ГиБ свободного пространства. Реальная нехватка места на хосте может дополнительно уменьшить доступный объём.

Динамический режим получает часть оставшегося доступного бюджета. Его общая ёмкость равна учтённому локальному объёму плюс текущий доступный рост; она может изменяться при изменении состояния хоста. Это изменение видимой ёмкости, а не только постепенное физическое заполнение диска фиксированного размера.

Для виртуального представления нужно согласовать общий объём и доступное место во всех поддержанных запросах. В частности, `GetDiskFreeSpaceExW` различает объём, доступный вызывающему пользователю, и сведения о свободном месте тома. Эти значения не всегда равны при квотах. [Документация Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw).

Показанные числа и ограничение записи используют одну политику. Подмена результата запроса свободного места без контроля записи не считается квотой.

## Общий бюджет физического тома

Расчёт объединяет диски всех управляемых контейнеров на одном физическом томе. Иначе разные контейнеры смогут независимо обещать один и тот же остаток. Состояние определяется по физическому тому, а не только по букве его текущей точки подключения.

Для согласованного снимка без незавершённых операций обозначим:

- `F` — фактически свободные байты хоста, доступные в контексте выполняемой записи;
- `B` — минимальный запас, который WinLayer оставляет хосту и служебным операциям;
- `U_i` — уже учтённый локальный объём виртуального диска;
- `Q_i` — настроенная фиксированная ёмкость;
- `R_i = max(0, Q_i - U_i)` — ещё не использованная часть фиксированной ёмкости.

Тогда для фиксированного диска предлагается:

```text
Свободно_i = min(R_i, max(0, F - B - сумма R_j остальных фиксированных дисков))
Всего_i = Q_i
```

Общий свободный остаток для динамических дисков:

```text
Остаток = max(0, F - B - сумма R_j всех фиксированных дисков)
```

Уже занятые данные всех дисков входят в занятое место хоста и потому уже исключены из `F`. Повторно вычитать `U_i` нельзя. Полный лимит `Q_i` тоже нельзя целиком вычитать из текущего свободного места: вычитается только незаполненная часть `R_i`.

При создании или увеличении фиксированного лимита проверяется, что сумма незаполненных фиксированных лимитов помещается в `max(0, F - B)`. Если хост позже занял этот запас, настроенная ёмкость не меняется молча: уменьшается доступное место, а панель показывает дефицит. Эти логические обязательства защищают место от других управляемых записей WinLayer, но не резервируют физические блоки против сторонних приложений хоста.

### Пример

На физическом диске сейчас свободно 500 ГиБ. Виртуальный `C:` имеет фиксированный лимит 200 ГиБ и уже использует 50 ГиБ. Запас для хоста и служебных операций составляет 20 ГиБ. Других фиксированных дисков нет, динамический `E:` пока пуст.

| Показатель | Значение |
| --- | --- |
| Неиспользованный лимит `C:` | 200 − 50 = 150 ГиБ |
| Доступно динамическому `E:` | 500 − 20 − 150 = 330 ГиБ |
| Уже занятые 50 ГиБ `C:` | Повторно не вычитаются: они уже учтены в исходных 500 ГиБ свободного места |

При записи ещё 10 ГиБ на `C:` физическое свободное место уменьшится на 10 ГиБ, но и незаполненный фиксированный лимит уменьшится на 10 ГиБ. Поэтому доступный рост `E:` останется прежним при отсутствии других изменений и накладных расходов.

## Несколько динамических дисков

Нельзя независимо назначить каждому весь остаток, одновременно называя его отдельным выделенным объёмом. Возможны две различные политики:

1. Разделять остаток по долям. Например, два равноправных динамических диска получают половину текущего свободного остатка каждый. Необязательный предел роста ограничивает долю, избыток перераспределяется остальным. Сумма доступных долей не превышает остатка. Доля относится к текущему свободному росту, а не гарантирует постоянную пропорцию накопленных данных.
2. Показывать общий свободный пул нескольким дискам. Тогда место явно является общим, а записи конкурируют за него. Складывать показанное свободное место этих дисков нельзя. Это отдельный режим интерфейса и учёта, не скрытая реализация первого варианта.

Для первого эксперимента достаточно одного динамического диска и нескольких фиксированных. При добавлении нескольких динамических предлагается начать с явного распределения по долям. Остановка контейнера сама по себе не освобождает фиксированные лимиты и не удаляет настроенные диски из распределения; освобождение бюджета является отдельным изменением конфигурации.

## Что учитывается в занятом объёме

Предлагаемая квота ограничивает физический объём локального хранения. Только читаемые файлы нижнего слоя не списываются с лимита. При копировании внешнего файла внутрь учитывается создаваемая локальная копия, даже если приложение меняет лишь несколько байтов. Поэтому сумма размеров файлов объединённого представления может отличаться от занятого объёма виртуального диска: это бюджет локальных данных, а не полноценная копия файловой системы хоста.

Для прототипа предлагается учитывать выделенное место верхнего слоя и временные файлы операций. Размеры логических файлов показываются отдельно. Дополнительные потоки, жёсткие ссылки, сжатие, разреженные файлы и файлы с отложенным удалением требуют согласованного учёта; неподдержанные способы выделения места нельзя объявлять охваченными квотой. Жёсткие ссылки между разными виртуальными дисками не должны использоваться для обхода лимита.

Реестр, метаданные и журналы контейнера имеют отдельный служебный учёт, также расходуют физический том и не должны расти без контроля. Их уже размещённые байты не вычитаются из `F` второй раз. Запас служебных операций — бюджет ещё возможного роста, а не повторный подсчёт существующих файлов.

## Запись и изменение настроек

Перед операцией, способной увеличить размещение, движок согласованно проверяет лимит диска и общий бюджет тома. Одновременные копирования и записи учитывают ещё не размещённые заявки на место, чтобы один остаток не был разрешён нескольким операциям. После фактического размещения заявка превращается в учтённое использование; при ошибке освобождается только неиспользованная часть. Формулы выше описывают состояние без таких заявок; реализация обязана включать их в расчёт без повторного вычитания уже выделенных блоков.

Проверяется не только обычный вызов записи, но и увеличение файла, отображение в память, подготовка локальной копии и другие поддержанные пути роста. Если выбранный движок не позволяет надёжно ограничить операцию, для неё нельзя заявлять строгую квоту. Наблюдение за размером папки после записи само по себе её не обеспечивает.

При реальном заполнении тома запись завершается штатной ошибкой, не перенаправляется в оригинал и не требует удаления чужих данных. Восстановление незавершённых операций сохраняет учёт. Полный откат всей установки этим не обещается.

Для прототипа изменения букв, источников чтения, режимов и лимитов предлагается применять при остановленной среде. Лимит нельзя уменьшить ниже уже учтённого использования. Прямое ручное изменение файлов контейнера снаружи требует повторного согласования учёта перед запуском; жёсткая квота не обещается для произвольных внешних записей в папку.

## Исключения для рабочих каталогов

Выбрано: исключения задаются в конфигурации каждого контейнера. Для правила хранятся видимый приложению путь, соответствующий внешний путь и режим доступа. Обычно пути совпадают, но явное разделение позволяет позднее подключить тот же рабочий каталог по другому виртуальному пути.

| Режим | Поведение |
| --- | --- |
| Обычная виртуализация | Чтение из объединения, запись в верхний слой и учёт в квоте виртуального диска |
| Прямой доступ | Чтение и запись в выбранный внешний каталог, без локальной копии |
| Только чтение | Чтение выбранного внешнего каталога, изменения отклоняются |

Пример: `D:\Work` доступен напрямую, поэтому изменения исходников сразу видны внешнему Git. Удаление файла приложением в таком каталоге тоже удаляет внешний файл; это следствие выбранного режима. Удаление самого контейнера содержимое исключения не удаляет.

Для вложенных правил предлагается приоритет наиболее конкретного каталога с проверкой границ пути: `D:\Work` не означает `D:\Workshop`. Ссылки файловой системы и альтернативные формы пути учитываются при разрешении доступа. Служебные каталоги движка и физические хранилища контейнеров не превращаются в обычные исключения для прикладного доступа.

В прямом каталоге запрос доступного места относится к его физическому хранилищу. Запись не расходует квоту верхнего слоя, однако уменьшает свободное место соответствующего физического тома и потому может уменьшить бюджеты контейнеров на нём. Исключение работает в пределах прав пользователя, а не выдаёт новые права доступа.

Смена режима каталога с уже существующими локальными изменениями требует явного решения, какие данные сохраняются. Автоматическое слияние не предлагается. Внешние папки после переноса контейнера привязываются заново при несовпадении окружения.

## Проверки прототипа

Проверяются фиксированный предел, динамический остаток, отсутствие двойного вычитания занятого места, несколько контейнеров на одном томе, одновременные записи, расход места внешним приложением, copy-on-write большого файла, удаление открытого файла и восстановление после сбоя. Для исключений проверяются реальное сохранение проекта, вложенные правила, сведения о свободном месте и сохранность внешней папки при удалении контейнера.

Это проектные правила; реализация и проверки ещё не выполнены.
